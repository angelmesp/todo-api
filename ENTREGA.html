Título: API REST de tareas (To-Do)
Tecnología: Node.js + Express
Modalidad: Individual
Versión de la imagen: 1.0

1. Aplicación construida

Se desarrolló una API REST pequeña de tareas. Permite crear, listar, consultar, actualizar y eliminar pendientes. Los datos se guardan en memoria para que el ejercicio sea fácil de ejecutar dentro de un contenedor.

MétodoRutaQué hace
GET/healthComprueba que el servicio está activo
GET/api/todosLista todas las tareas
GET/api/todos/:idConsulta una tarea
POST/api/todosCrea una tarea
PUT/api/todos/:idActualiza título o estado
DELETE/api/todos/:idElimina una tarea

Ejemplo de cuerpo para crear:

{
  "title": "Estudiar DevSecOps",
  "completed": false
}

2. Cómo se ejecuta

En local

cd todo-api
npm install
npm start
curl http://localhost:8080/health
curl -X POST http://localhost:8080/api/todos -H "Content-Type: application/json" -d '{"title":"Entregar actividad 4"}'
curl http://localhost:8080/api/todos

Con Docker

docker build -t angelmesp/todo-api:1.0 .
docker run --rm -p 8080:8080 angelmesp/todo-api:1.0

3. Registro de prompts de IA

La IA se usó como apoyo. Todo se revisó y se ajustó antes de dejarlo en el proyecto.

#PromptQué aportóQué se hizo después
1 Ayúdame a crear una API REST sencilla de tareas en Node.js. Debe tener crear, listar, actualizar y eliminar. Explícame la estructura antes de generar código. Separar servidor, rutas y almacén en memoria. Se aceptó esa estructura porque es fácil de explicar y de analizar.
2 Revisa este código y dime qué problemas de calidad podría detectar Sonar. No lo reescribas completo; explícame primero los problemas. Falta de validación, errores inconsistentes y middleware incompleto. Se validó title/completed y se unificaron las respuestas de error.
3 Genera un Dockerfile sencillo y seguro. Explícame cada instrucción. Alpine, npm ci, usuario no root y NODE_ENV=production. Se usó node:20.19.4-alpine3.21 y el usuario appuser.
4 Revisa mi README y dime si otra persona podría ejecutar la aplicación solo con esas instrucciones. Faltaban ejemplos de curl y el comando exacto de Docker. Se completó el README con tabla de endpoints, local y Docker.
5 Trivy reporta este hallazgo en el Dockerfile: DS-0026 HEALTHCHECK. Explícame el riesgo y cómo corregirlo. Sin HEALTHCHECK Docker no sabe si el proceso sigue sano. Se agregó HEALTHCHECK contra /health y se volvió a escanear.

Decisión técnica con apoyo de IA: no usar node:latest. Una etiqueta concreta permite reproducir el build y reduce sorpresas en Trivy.

4. Calidad con Sonar

Archivo de configuración: sonar-project.properties. Proyecto analizado: todo-api.

Se revisaron hallazgos típicos de Sonar y se corrigieron al menos dos:

  1. Validación de entrada (bug / reliability). Se podía crear una tarea sin title o con texto vacío. Ahora title es obligatorio y completed, si se envía, debe ser boolean.
  2. Manejo de errores (code smell / reliability). Las rutas inexistentes y los fallos internos no tenían respuesta uniforme. Se agregó 404 de ruta y un middleware 500.

Si el análisis no reporta más hallazgos relevantes, queda documentado que el código ya incluye esas correcciones.

5. Docker

La imagen se construye con el Dockerfile de la raíz. Puntos de seguridad:

  • FROM node:20.19.4-alpine3.21 — base pequeña y versionada
  • npm ci --omit=dev — solo dependencias de producción
  • USER appuser — el proceso no corre como root
  • HEALTHCHECK — comprueba /health
docker build -t angelmesp/todo-api:1.0 .
docker run --rm -p 8080:8080 angelmesp/todo-api:1.0

Comprobación: GET /health responde {"status":"ok"} y el CRUD funciona.

8. Reflexión final

El problema principal no fue programar el CRUD, sino completar el flujo hasta publicar una imagen revisada. Al principio el código aceptaba datos inválidos; la revisión de calidad dejó claro que eso es un hallazgo real, no un detalle menor. Se corrigió la validación y el manejo de errores. Después, Docker obligó a pensar en usuario no root y en no copiar node_modules del host. Trivy mostró un LOW por falta de HEALTHCHECK; se agregó y el segundo escaneo quedó en cero. También quedó claro que la seguridad de la imagen depende mucho de la base: usar latest es cómodo, pero una etiqueta concreta y reciente es más controlable. Publicar en Docker Hub cierra el ciclo: el mismo artefacto que se escanea es el que se entrega. Lo aprendido del flujo DevSecOps es que calidad y seguridad no van al final como un extra, sino como pasos que cambian el código, el Dockerfile y la versión publicada.
